# Forge 언어 평가와 수정 후기 — 2026-09-30

평가 대상은 이 로컬 모노레포의 기준 커밋 `ed0a3a6`과 이번 작업의 변경 사항이다. README에 안내된 분리 저장소의 최신 구현은 조사하지 않았다. 따라서 이 평가는 Forge 전체 생태계의 최신 상태를 뜻하지 않는다.

## 냉정한 평가

**구현 완성도에 대한 주관적 종합 평가는 4/10이다.** 프로세스와 코루틴을 결합하려는 방향, 작은 C 백엔드, 실제로 동작하는 self-hosting은 의미 있는 성과다. 그러나 언어의 핵심 약속인 계산 정확성, 정적 안전성, 실행 재개, 장애 복구를 신뢰할 근거가 부족했다. 이번 수정으로 여러 재현 가능한 결함을 제거했지만 실서비스에 사용할 정도로 성숙했다고 평가하지 않는다.

| 항목 | 판단 | 근거 |
|---|---|---|
| 설계와 실험 가치 | 좋음 | AOT와 프로세스/코루틴 모델을 작은 구현으로 탐색할 수 있음 |
| 컴파일러 정확성 | 미성숙 | 수정 전 `x * 0` 오컴파일, 상수 연산 중 컴파일러 종료, 리터럴 정밀도 손실 |
| 타입·소유권 안전성 | 부족 | 독립적인 완전한 의미 검사 단계가 없고 `--check`가 타입 오류와 move 후 사용을 통과시킴 |
| 동시성·장애 복구 | 부족 | 공유 상태의 동기화가 불완전하고 supervisor 정책은 등록만 됨 |
| 검증 | 개선됨 | 기존 CI는 C 빌드만 검사했으나 이번에 실행 결과·메모리·큐 회귀 테스트를 추가함 |
| 성능 주장 | 범위 제한 필요 | HTTP 벤치마크의 주요 경로는 캐시 응답을 보내는 C 함수로, 언어 전체의 비교가 아님 |

사용 후기는 “작게 동작하는 언어를 만들고 실험하는 데는 유용하지만, 문서에 나온 기능 목록만 보고 안전성과 실행 의미를 믿으면 안 된다”이다. 기능을 더 늘리기보다 언어 의미와 회귀 검증을 먼저 확립하는 것이 다음 개발의 우선순위다.

## 실제로 확인하고 수정한 문제

| 문제 | 수정 전 증거 | 수정 |
|---|---|---|
| 곱셈의 잘못된 단순화 | `fn zero(x: int): int { return x * 0; }`에 7을 전달하면 7 출력 | 잘못된 규칙 제거. 함수 호출 등 피연산자의 효과도 보존 |
| 상수 정수 연산의 미정의 동작 | `(-9223372036854775807 - 1) / -1`과 나머지 연산이 `--check`에서 SIGFPE 발생 | 덧셈·뺄셈·곱셈 범위와 나눗셈 예외를 계산 전에 검사 |
| AST 재할당 낭비 | 접을 수 없는 이항식까지 새 노드를 생성하고 기존 노드를 해제 | 접기 성공 시 기존 노드를 재사용하고 실패 시 그대로 유지 |
| 잘못된 타입 전파 | 비교식에 왼쪽 피연산자 타입을 부여하고 미해결 산술식도 정수로 간주 | 비교식 bool 지정, 미해결 산술식은 보수적으로 유지, 정수 항등식의 타입 조건 강화 |
| 숫자 출력·파싱 오류 | `5.0`이 C의 `5`로 출력되어 정수 나눗셈 발생, `%g`의 정밀도 손실, 긴 리터럴을 63자로 자름 | float는 17자리와 소수 표기를 유지하고 int는 `INT64_C` 사용. 전체 리터럴 파싱과 범위 오류 진단 |
| 코루틴 재개 번호 충돌 | 두 번의 `yield`가 생성 C의 `duplicate case value`로 컴파일 실패 | 함수 전체에 하나의 재개 번호 카운터를 사용하여 중첩 if/while까지 처리 |
| 코루틴 초기화식의 중복 실행 | yield가 없는 본문에서는 spawn 때와 실행 때 같은 초기화식을 평가 | 코루틴 본문에서 한 번만 평가. 불필요한 사전 초기화 코드와 순회 함수 제거 |
| await의 대기 상태 손실 | I/O 대기 설정 뒤 `fr_yield`가 상태를 바꾸고 다음 번호로 넘어감 | WAITING_IO를 반환하고 같은 재개 위치에서 준비 여부 재확인 |
| arena 포인터 무효화 | 하나의 버퍼를 `realloc`하여 기존 문자열 포인터가 더는 유효하지 않을 수 있음 | 주소가 이동하지 않는 연결 블록으로 전환, 정렬·크기 오버플로 검사, reset 후 블록 재사용 |
| 큐 steal의 선형 탐색 | 매 steal마다 꼬리 이전 노드를 찾기 위해 목록 전체 순회 | OMO로 양방향 링크와 공통 unlink 경로 구현. FIFO pop/LIFO steal 유지 |
| CLI 배열 초과·잘못된 옵션 | `-I`/`-l` 반복 횟수 제한 없음, 누락·알 수 없는 옵션 무시 | 32개 한도 검사와 오류 진단, 복수 입력·누락 값 거부, help 지원 |
| 증분 빌드 누락 | stdlib와 bootstrap 단계 산출물의 파일 의존성이 불충분 | native 출력에 forge_std 의존성을 추가하고 stage1/stage2 파일 의존성을 명시 |
| 문서와 구현 불일치 | 메모리에서만 C 생성, 선점 스케줄링, 자동 장애 복구를 구현한 것으로 표현 | 실제 임시 C 파일 경로와 협력적 실행, 미구현 복구를 README에 명시 |

오버플로하는 정수식을 접지 않는 것은 컴파일러 자체를 보호하는 변경이다. 실행 시 정수 오버플로를 검사하거나 wrapping arithmetic을 정의하는 변경은 아니다. 런타임 정수 오류의 언어 의미는 여전히 별도로 정해야 한다.

arena는 이전 블록도 유지하므로 성장 후 메모리 사용량이 늘 수 있고 reset 비용은 블록 수에 비례한다. 대신 기존 포인터를 보존하고 다음 요청에서 블록을 재사용한다. 포인터는 reset 또는 destroy 이후에는 사용할 수 없다.

## OMO 사용 결과

설치된 `oh-my-openagent` 플러그인의 `Sisyphus - ultraworker`를 `opencode run`으로 실행했다. 기본 모델 식별자 오류와 기존 공급자의 API 연결 실패가 있어, 이미 인증된 OpenRouter의 `openai/gpt-5.6-sol`을 명시한 실행으로 완료했다. 전역 설정은 변경하지 않았다.

OMO가 수정한 범위는 `runtime/work_queue.c`, `runtime/work_queue.h`, `tests/work_queue_test.c`, `benchmark/work_queue_bench.c`이다. 주 작업자가 그 변경을 읽고 검토한 뒤 CMake/CTest에 통합하고 기존 구현과 비교했다. 벤치마크에는 비교 크기 지정 옵션과 시간 차 계산을 추가했다. 컴파일러·arena·문서·CI 수정은 주 작업자가 수행했다.

## 성능 확인

환경: Linux 6.8.0-139-generic x86_64, GCC 13.3.0. 기존 큐는 `ed0a3a6`에서 추출했고 동일한 벤치마크, `-std=c11 -O2 -pthread` 조건으로 각각 빌드했다. **이전/수정/이전/수정** 순서로 실행했다. 각 실행은 미리 채운 큐를 다섯 번 비워 가장 짧은 시간을 기록한다. 아래는 두 실행의 범위이며 단위는 작업 하나를 steal하는 데 걸린 ns이다.

| 큐 길이 | coroutine 이전 | coroutine 수정 | native 이전 | native 수정 |
|---:|---:|---:|---:|---:|
| 1,000 | 605–2,188 | 29–59 | 614–1,708 | 31–63 |
| 10,000 | 5,957–6,727 | 28–57 | 7,416–7,437 | 31–41 |
| 20,000 | 14,428–14,539 | 21–36 | 16,278–16,489 | 22–31 |

기존 구현은 큐 길이에 따라 비용이 증가한다. 수정 구현은 목록 순회가 사라져 큐 길이에 비례한 증가가 사라졌다. 측정은 단일 소비자의 큐 제거 연산만 다루며 malloc/free와 mutex 비용을 포함한다. CPU를 고정하지 않은 공유 환경이라 절대 시간에는 변동이 있고, 이 수치를 전체 스케줄러 또는 HTTP 처리량의 향상 배수로 해석해서는 안 된다. HTTP 비교 벤치마크는 이번에 재측정하지 않았다.

수정된 `bench_coro`의 100,000 코루틴 예제도 정상 종료했다. 전체 프로세스 경과 시간은 한 번의 실행에서 약 0.078초였으며 성능 보장이나 반복 A/B 결과로 사용하지 않는다. 출력의 `coro bench ms`는 생성 구간만 측정하므로 전체 실행 시간과 다르다.

재실행:

```bash
cmake --build build --target work_queue_bench
./build/bin/work_queue_bench 20000
```

## 검증 결과

- Release 전체 빌드와 예제 빌드 성공.
- CTest 4개 묶음 통과: optimizer, arena, work queue, compiler.
- compiler 묶음의 Python 테스트 11개 통과. 네이티브 출력 실행, 중첩 yield, 초기화 부작용, 지연된 TCP 데이터에 대한 await, CLI 오류 등을 포함한다.
- 큐 두 종류 각각 20,000개의 작업을 4개 소비 스레드가 정확히 한 번씩 꺼내는 테스트 통과.
- optimizer, arena, work queue의 독립 테스트를 AddressSanitizer와 UndefinedBehaviorSanitizer로 검증하여 통과.
- self-hosting stage1/stage2, match/control_flow 출력 생성, stage3/stage4의 C 출력 고정점 비교 통과. 새 의존성을 적용한 후 실제로 단계들을 재빌드했다.
- hello, coroutines, functions, match, ownership, use_module, use_library 실행 성공.
- `git diff --check` 통과.

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

Python 3이 없으면 현재 CMake 설정에서는 compiler 회귀 테스트를 등록하지 않는다. 로컬에는 처음에 CMake가 없어 사용자 경로에 CMake/Ninja를 설치해 빌드했다. OpenCL 라이브러리는 없어 GPU 경로를 검증하지 않았다. Windows/macOS 실행과 Lean 증명 빌드는 이번 검증 범위에 포함하지 않았다. 기존의 일부 빌드 경고도 남아 있다.

## 남아 있는 설계 과제

이번 수정은 언어의 모든 문제를 해결한 전면 재작성은 아니다. 다음 결함과 공백은 현재도 남아 있다.

1. **의미 검사 단계:** `native main { let x: int = "hello"; }`와 move 후 사용이 `--check`에서 성공한다. 심볼·스코프·함수 시그니처·타입·소유권을 codegen과 분리해 검사해야 한다.
2. **스케줄러 동기화:** `running`, coroutine 상태, `on_queue`, 큐 count 등을 서로 다른 스레드에서 읽고 쓰는 경로가 단일한 잠금/원자성 규칙을 따르지 않는다. 큐 내부 잠금 테스트가 전체 스케줄러의 경쟁 상태 부재를 증명하지 않는다.
3. **실행 및 메시지 의미:** `recv`는 worker를 condition variable에서 블로킹할 수 있다. mailbox 256개 초과에 대한 전송 실패·payload 처리 정책도 불충분하다. backpressure와 정지·취소·오류 전파를 정의해야 한다.
4. **코루틴 제어 흐름:** 이번에 yield/await 재개를 고쳤지만 중첩 지역 변수의 상태 보존, for/match/break/continue 등의 모든 문장이 coroutine emitter에서 지원되는 것은 아니다. 상태 기계로 내리는 별도 단계가 필요하다.
5. **실제 선점과 복구:** 현재 reduction budget은 coroutine 함수 호출 사이의 예산이다. 함수 안에서 긴 계산을 하면 강제 중단하지 않는다. supervisor 역시 정책을 저장할 뿐 오류 뒤 실행 상태를 복원하는 경로가 없다.
6. **메모리·소유권 규약:** `own`, arena 문자열, 함수 반환 문자열의 수명과 해제 주체를 정리해야 한다. 현재 move 추적은 제어 흐름과 스코프 전체를 정밀하게 분석하지 않는다.
7. **증명과 실제 구현 연결:** Lean의 무한 정수 표현식 모델과 C의 int64/부작용/부동소수점 의미 사이에 검증된 연결이 없다. 고정점 self-hosting도 컴파일러 의미의 정확성을 증명하지 않는다.

다음 개발은 의미 검사 → 스케줄러 동기화 → 코루틴 lowering과 오류 복구 순서가 적절하다. 이 기반이 정리된 뒤 같은 기능·요청 파싱·오류 처리를 갖춘 워크로드로 성능을 비교해야 한다.
