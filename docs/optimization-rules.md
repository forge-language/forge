# Forge HTTP 서버 최적화 규칙

**작성일:** 2026-08-06
**대상:** `stdlib/http.c` (`fr_http_serve_mt`, `fr_http_serve_hybrid`, 관련 accept/recv 경로)
**성격:** 이 문서는 성공한 최적화가 아니라, **이번 세션에서 시도했다가 측정으로 기각된 두 가지 변경**을 규칙화한 것이다. 두 변경 모두 syscall 수와 컨텍스트 스위치 수는 줄였지만 처리량은 떨어졌다. "더 적은 syscall = 더 빠름"이라는 직관이 이 워크로드에서는 틀렸다는 것이 핵심 교훈이다.

---

## 1. 결론 먼저

현재 `stdlib/http.c`의 구조 — SO_REUSEPORT 워커별 소켓 + epoll/kqueue 기반 accept 배칭 + 사전 캐시된 응답 — 는 이번 세션에서 시도한 대안들보다 모두 빠르거나 같았다. **코드는 원래 커밋 상태로 되돌렸다.** 아래 두 규칙은 "왜 손대면 안 되는가"를 데이터로 남겨서, 같은 실험을 반복하지 않도록 하기 위한 것이다.

---

## 2. 규칙 1 — epoll/kqueue 기반 accept 배칭을 블로킹 `accept()` 루프로 바꾸지 말 것

### 시도한 변경

`http_serve_event_loop()` (epoll_wait로 리스닝 소켓 readiness를 기다린 뒤 EAGAIN까지 accept를 반복하는 구조)를, 워커마다 자신의 리스닝 소켓에 블로킹 `accept()`를 거는 단순 루프로 교체했다. SO_REUSEPORT 워커 하나는 커널이 정확히 하나의 소켓으로만 연결을 해시하므로, "감시할 fd가 하나뿐인데 epoll을 쓸 이유가 있나"라는 것이 가설이었다.

### 측정 결과 (코어 격리, 8 워커 vs 8 코어 wrk 클라이언트, 서버는 코어 0-7, wrk는 `taskset -c 8-15`)

| 구성 | Requests/sec (3회) |
|------|---------------------|
| epoll 기반 (원본) | 248,289 / 246,820 / 252,923 |
| 블로킹 accept 루프 | 173,976 / 178,152 / 164,048 |

**처리량 -31%.** 서버와 클라이언트가 같은 16코어를 나눠 쓰는 환경에서 측정한 첫 결과(-26~28%)도, 클라이언트/서버를 다른 코어로 완전히 격리한 재측정에서도 동일한 방향으로 나왔다 — 즉 "wrk 클라이언트가 CPU를 뺏겨서 생긴 착시"가 아니라 서버 쪽의 실질적 손실이다.

### syscall/컨텍스트 스위치는 정반대 방향으로 움직였다

`strace`와 `/proc/<pid>/status` (voluntary_ctxt_switches)로 확인한 연결당 평균값:

| 구성 | syscalls/연결 | 컨텍스트 스위치/요청 |
|------|----------------|------------------------|
| epoll 기반 | ~6 | 0.46 |
| 블로킹 accept 루프 | ~4.1 | 0.11 |

블로킹 accept 쪽이 syscall도 30% 적고 컨텍스트 스위치도 4배 이상 적었다 — **그런데도 처리량은 더 낮다.** 처음 세웠던 가설("블로킹 accept는 epoll의 웨이크업 상각(amortization)을 잃어서 컨텍스트 스위치가 늘어날 것이다")은 이 측정으로 완전히 기각됐다.

### 왜 그런가 (추정)

epoll_wait가 리스닝 소켓 하나의 readiness로 깨어난 뒤, EAGAIN이 나올 때까지 accept를 계속 뽑아내는 구조는 **커널 accept 큐에 쌓인 연결들을 한 번의 스케줄링 웨이크업 뒤에서 한꺼번에 드레인**한다. 반면 블로킹 accept 루프는 연결 하나를 처리할 때마다 accept() 자체가 블로킹 syscall이라 스레드가 커널에 진입/이탈하는 비용을 매 연결마다 지불한다 — syscall 횟수 자체는 적어도, accept 각각이 스케줄러 관점에서 "블로킹 대기 → 깨어남"을 반복하는 무거운 경로이기 때문으로 보인다. (perf_event_paranoid=4로 이 환경에서는 `perf stat`으로 정밀 검증은 불가능했다.)

### 규칙

> 연결 처리량이 많은(connection-per-request) 서버에서 SO_REUSEPORT 워커가 자신의 리스닝 소켓 단 하나만 감시하더라도, epoll/kqueue readiness 배칭을 블로킹 accept 루프로 교체하지 말 것. syscall/컨텍스트 스위치 수가 줄어드는 것은 이 워크로드에서 처리량과 반대 방향으로 움직이는 지표이므로, 그것만 보고 "최적화됐다"고 판단하지 말 것.

## 3. 규칙 2 — 캐시된 응답(fire-and-forget) 경로에 매 연결마다 요청 전체를 읽는 로직을 넣지 말 것

### 시도한 변경

`serve_client()`가 원래는 non-blocking 소켓에 대해 recv를 한 번만 호출하고 결과를 버린 뒤 캐시된 응답을 바로 보내는 구조였다. 이를 "요청을 실제로 다 읽고, 응답이 완전한 헤더(`\r\n\r\n`)까지 도착했는지 확인하며, 도착이 늦으면 `SO_RCVTIMEO`로 5초 제한을 건다"는 더 견고한 버전(`recv_until_headers` + 매 연결 `setsockopt(SO_RCVTIMEO)`)으로 바꿨다.

### 측정 결과

epoll 구조를 그대로 유지한 채 이 변경만 적용해도 처리량이 떨어졌다 (동일 A/B 하네스 기준, epoll 구조 복원본이 여전히 원본 대비 -30% 근처로 나옴). 즉 규칙 1의 손실 전부가 accept 방식 때문이 아니라, 이 recv 강화 로직 자체도 상당 부분을 차지한다.

### 왜 그런가

- 연결마다 `setsockopt(SO_RCVTIMEO)` 호출이 추가된다 (원본은 이 호출이 아예 없었다).
- `recv()`가 필요하면 여러 번 반복되는 루프로 바뀐다 (원본은 정확히 1번).
- 이 벤치마크 워크로드는 요청 본문을 실제로 파싱하지 않고 고정 응답만 돌려주므로, 요청을 "완전히" 읽어야 할 기능적 이유가 없다 — 즉 이 강화는 이 경로에서 얻는 이득 없이 비용만 추가한다.

### 규칙

> 요청 내용과 무관하게 고정된 캐시 응답만 돌려주는 fire-and-forget 경로에는, slowloris류 방어를 위한 "요청 전체를 읽고 타임아웃을 건다"는 로직을 넣지 말 것. 그런 방어가 필요하다면 요청을 실제로 파싱해서 사용하는 경로(`fr_http_accept` 등 단일 연결 API)에만 적용하고, 대량 처리량이 목표인 캐시-응답 경로와는 분리할 것.

## 4. 측정 방법론 규칙 (이번 세션에서 확립된 것)

1. **컴파일 산출물은 diff로 재빌드되지 않을 수 있다.** `bench_server`는 일반 C 타겟이 아니라 `forge` 컴파일러를 호출하는 `add_custom_command`로 생성된다. stdlib/runtime C 코드를 바꾼 뒤에는 반드시 `cmake --build build --target forge_std forge_runtime bench_server`처럼 명시적으로 다시 빌드할 것 — mtime을 확인하지 않으면 이전 바이너리로 벤치마크하게 된다.
2. **비교는 항상 A/B/A/B로, 같은 세션에서.** 단일 전/후 숫자는 머신 드리프트와 구분이 안 된다. `/tmp`에 여러 버전의 바이너리를 나란히 두고 라운드로빈으로 번갈아 실행해서 분포를 비교할 것.
3. **클라이언트와 서버가 코어를 공유하면 결론이 뒤집힐 수 있다.** 이 머신은 16코어이고 wrk 클라이언트와 서버 워커가 기본적으로 같은 코어 풀을 쓴다. 의심스러운 결과는 서버를 `fr_thread_pin_cpu`로 코어 0-7에, wrk를 `taskset -c 8-15`로 격리해서 재검증할 것. (이번 세션에서는 격리 전/후 결론이 바뀌지 않았지만, 격리 없이 내린 결론을 최종으로 삼지 말 것.)
4. **syscall 수 / 컨텍스트 스위치 수는 처리량의 대리 지표가 아니다.** 규칙 1이 정확히 이 실패 사례다 — 두 지표 모두 개선됐는데 처리량은 악화됐다. 최종 판단 기준은 항상 실제 처리량(req/s) A/B 측정이어야 한다.
5. **정리(cleanup)를 잊지 말 것.** 백그라운드로 띄운 서버는 `pkill -x <binary-name>`으로 이름 매칭해서 종료할 것 — `pkill -f <path>`는 실행 중인 벤치마크 스크립트 자신의 커맨드라인과 매치되어 스크립트 자체를 죽일 수 있다 (이번 세션에서 실제로 발생, exit 144).
